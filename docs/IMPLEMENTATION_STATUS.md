## 6B-C loyalty rules - documentation status (2026-11-21)
**Approved rules** (`DECISIONS.md` #15 and #16, mirrored in `PRODUCT.md`, `ROADMAP.md`, `DATABASE.md`): 1 stamp per confirmed purchase (`purchasesPerStamp` deprecated; conversion only via a new programme version); stamp-only purchase amount optional, required for points; points use floor with integer arithmetic, rate <= 2 decimals; money in integer millimes (API decimal strings, <= 3 dp); amount stored on the transaction header; explicit earning-rate snapshot required; history authoritative, never recalculated; multiple rewards in versioned programme config, no codes/inventory; redemption = merchant-selected, cost deducted, surplus preserved, own `redemption` category; reversal = owner, any time, full only, once, idempotent, final (cannot be reversed), required reason <= 500 chars, never negative; repeat-scan warning (10 minutes) is warning-only with explicit confirmation; no default caps; no expiry in R1; unreachable `limits.maxPerTransaction` dropped. Release 1 phone numbers are unverified unique identifiers (self-registration and merchant-assisted); OTP deferred to Release 2.

**Verified:** programme-configuration immutability is **not** guaranteed by the database (no update-blocking trigger/privilege; FK restricts deletion of referenced configurations; app code only inserts). Hence the earning-rate snapshot is necessary.

**Behaviour before the 2026-11-21 implementation (historical; backend replaced, frontend scanner unchanged):** merchant endpoints `customers/resolve-for-transaction`, `transactions/calculate-earnings`, `transactions`, `transactions/redeem-reward`; scanner flow in `frontend/src/features/loyalty/scanner/`.
